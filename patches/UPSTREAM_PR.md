**Title:** `feat(network): accept IP literals and CIDR ranges in allowedDomains / deniedDomains`

## Body

Closes #65 (part 1 — the IP/CIDR allow/deny half; the "disable network
isolation" half of the RFE is a separate, larger question).

### Problem

`network.allowedDomains` / `network.deniedDomains` only accept domains,
`*.domain` wildcards and (by accident of the pattern check) bare IP literals
as exact matches. `isValidDomainPattern` rejects any entry containing `/`, so
network ranges cannot be expressed at all:

```js
NetworkConfigSchema.parse({ allowedDomains: ["10.22.86.0/24"] })
// Invalid domain pattern. Must be a valid domain (e.g., "example.com"), ...
```

This blocks common intranet policies ("allow the whole lab/VLAN/DC range",
"deny all of 10.0.0.0/8 for agent traffic") and — as #65 points out — the
private-network threat model is precisely about IP ranges, not domain names.

The runtime already has all the machinery: `parseAddressRange()` /
`addRange()` / `addressInSet()` over `net.BlockList` (`src/sandbox/address.ts`)
are used for `deniedResolvedAddresses` and for the parent-proxy `NO_PROXY`
matcher (hostname suffix **and CIDR** — `src/sandbox/parent-proxy.ts`), and the
resolved-address guard's `buildRuleSet()` already consumes CIDR strings via
`addRange()`. Only the domain-list entry validation and the destination
matcher are missing it.

### Design

Add IP-literal/CIDR as a first-class entry form in both lists. Three changes,
all in existing modules:

**1. Entry validation (`src/sandbox/sandbox-config.ts`)**

Accept an entry when the port-stripped host part parses as an address range
(`parseAddressRange(splitDomainPatternPort(val).hostPattern) !== undefined`)
instead of only via `isValidDomainPattern`. Applied to both
`domainPortPatternSchema` (allowedDomains) and `deniedDomainPatternSchema`;
the entry-error text (`ALLOWED_DOMAIN_ENTRY_MESSAGE` and the deniedDomains
variant) documents the forms, including the bracketed port spelling for
IPv6 ranges.

Resulting entry grammar (consistent with `deniedResolvedAddresses`' documented
"IPv4 or IPv6, unbracketed" syntax):

| entry | verdict |
|---|---|
| `10.22.86.5` | accepted (already was — kept) |
| `10.22.86.0/24`, `10.0.0.0/8` | **new** — IPv4 CIDR |
| `10.22.86.0/24:8080` | **new** — port-scoped CIDR (port split is unchanged) |
| `[2001:db8::1]` | accepted (already was — kept) |
| `2001:db8::1` | **new** — bare unbracketed IPv6 literal (was rejected as ambiguous; `deniedResolvedAddresses` already used this spelling) |
| `2001:db8::/32` | **new** — IPv6 CIDR, unbracketed |
| `[2001:db8::/32]:8080` | **new** — port-scoped IPv6 CIDR, port bracketed (same form as the bracketed literal `[2001:db8::1]:443`) |
| `[2001:db8::]/32` | rejected (bracketed form is unrepresentable through the port splitter — same as today's `host:port` ambiguity handling; unbracketed is the documented spelling) |
| `2001:db8::/32:8080` | rejected (unbracketed port-scoped IPv6 CIDR is indistinguishable from an address — the validation error points at the bracketed form) |
| `evil.com/24`, `10.0.0.0/33`, `2001:db8::/129`, `*.10.0.0.0/8` | rejected (garbage / bad prefix / wildcard-IP) |

**2. Destination matching (`src/sandbox/domain-pattern.ts`)**

`matchesDomainPattern()` gets a CIDR branch: entries containing `/` are
judged by `BlockList` membership (cached per pattern) — but only against
destinations that are IP spellings: a strict IP, or a pure numeric IPv4 form
(decimal `169236173`, dotted `127.1`) that `canonicalizeHost()` resolves to
the same address. Names never match a range: anything else is refused before
the membership check, which is the documented "IP-literal destinations only,
never names" contract and the same treatment exact literals get. Production
behavior is unchanged — `filterNetworkRequest()` canonicalizes the
destination before pattern matching, for every entry kind — and a name is
judged by where it actually resolves (change 3).
`matchesDomainPatternWithPort()` is unchanged; the existing `:port` split
composes with CIDR for free, including the bracketed IPv6 form
`[2001:db8::/32]:8080`.

Because every existing caller of `matchesDomainPattern` (allow/deny decision,
credential sentinel injection, MITM routing) goes through this one function,
CIDR entries are correct everywhere with no call-site changes.

**3. Resolved-address guard feed (`src/sandbox/domain-pattern.ts`)**

`ipLiteralRules()` currently drops every entry whose host part isn't
`isIP()` — so CIDR entries would never reach the guard. Change the filter to
`parseAddressRange(hostPattern) !== undefined`; the guard's `buildRuleSet()`
already consumes CIDR via `addRange()`. Consequences (all mirroring the
long-standing IP-literal semantics):

- a `deniedDomains` CIDR refuses hostnames that resolve into the range
  (e.g. `deniedDomains: ["10.22.86.0/24"]` stops `db.corp` resolving to
  `10.22.86.5`);
- an `allowedDomains` CIDR carves a name out of the built-in denials exactly
  like an exact IP literal does (loopback/link-local/metadata carve-outs
  remain an explicit choice, as with literals today).

### Security

No new attack surface beyond an explicit configuration choice:

- CIDR entries never match names at the pattern layer — the range branch
  refuses any destination that is not an IP spelling before the membership
  check — so DNS rebinding of an allowed name is still governed by the
  resolved-address guard, whose built-in denied classes (loopback,
  unspecified, link-local, multicast, broadcast, cloud-metadata, own
  interface addresses) are untouched. A name that spells an allowed range in
  decimal (e.g. `169236173` = 10.22.86.205) is judged by the address it
  resolves to, asserted by test.
- The matcher canonicalizes IP spellings before the range check, so
  `2852039166` (= 169.254.169.254) cannot sneak past an entry written as
  `169.254.169.254` — the same property exact literals already have via
  `canonicalizeHost`.
- Private-use ranges (RFC 1918/ULA/CGNAT) remain *intentionally* outside the
  guard's built-in denials; listing one in `allowedDomains` is the same kind
  of explicit choice as allowing an exact private IP literal today.

### Tests

New unit tests around the three seams (all pass on this branch):

- schema: accepts the table above, rejects the malformed rows (incl. the
  unbracketed port-scoped v6 CIDR); `*.com` / `*` policy unchanged;
- matcher: in/out-of-range v4+v6, port scoping (`:8080` honored and
  mismatched, bracketed `[2001:db8::/32]:8080`), numeric-spelling
  canonicalization, names never match CIDRs (incl. names carrying a decimal
  address inside them), IPs never match domains, existing wildcard/exact
  behavior untouched;
- guard: name resolving into a denied CIDR refused; name resolving outside it
  allowed; a name that spells an allowed range judged by the address it
  resolves to; allowed CIDR carving out a built-in denial (127.0.0.0/8) like
  literals do; `ipLiteralRules` carries CIDRs with their port.
